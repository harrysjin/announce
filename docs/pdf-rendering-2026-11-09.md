# 원형 장음 표시의 PDF 렌더링 검증 — 2026-11-09

## 문제와 재현

기존 출력은 원문 위에 채워진 `Circle` 주석을 올리고 `Multiply` 혼합 모드에 의존했다. 혼합 모드를 적용하는 뷰어에서는 검은 획이 유지되지만, 주석 모양을 다시 생성하거나 보통 합성으로 처리하면 파란 원이 글자 위에 합성되어 획이 회청색으로 보일 수 있다. 웹 SVG 미리보기와 PDF 주석도 서로 다른 그리기 경로였다.

수정 전에 먼저 만든 렌더링 회귀 검사 6개 중 3개가 실패했다. 원이 페이지 본문 벡터로 존재하지 않았고, `Multiply`를 `Normal`로 바꾼 재현에서 원래 검은 픽셀 87개가 변했으며, 주석 표시를 끈 출력과 켠 출력이 달랐다. 이것은 특정 macOS 뷰어를 실행한 결과가 아니라 혼합 모드 의존성을 격리한 회귀 재현이다.

## 최종 그리기 방식

- 원문을 가리지 않는 페이지에서는 원을 기존 페이지 내용 뒤에 벡터로 추가한다. 원래 텍스트가 그 위에 그대로 그려진다.
- 원이 불투명 채움·이미지·그라데이션 아래에 가려지는 페이지에서는 원을 위에 추가하되, 원래 글자 획과 1.5pt 여유 영역을 벡터 클립으로 제외한다. 원본의 작은 타일을 4배 해상도로 분석하며, 분석 픽셀은 출력 PDF에 넣지 않는다. 배경과 조금이라도 다른 픽셀을 감지하여 옅은 안티앨리어싱 경계도 보호한다.
- 배경을 확실히 구별할 수 없는 타일, 글자가 추출되지만 잉크가 감지되지 않는 경우, 작업 한도에 도달한 경우에는 글자 경계 상자 전체와 0.5pt 여유를 제외한다. 이 경우 글자 주변의 원 일부가 비거나 여백이 넓어질 수 있으며, 보호 영역이 원 전체를 덮으면 원이 보이지 않을 수 있다. 원문 글자를 덧칠하지 않는 쪽으로 처리한다.
- 자동 사전 표시, 규칙 표시, 수동 추가·이동·크기 조절에 같은 함수를 사용한다. 색상·불투명도·전체 크기 설정도 같은 경로를 따른다.
- 출처 정보는 기존과 같은 `Circle` 주석에 남긴다. 새 주석은 유효한 빈 `AP/N` 스트림을 가지므로 화면에 원을 다시 칠하지 않는다. 색상·불투명도·사전 및 규칙 URL·팝업 설명은 유지되며, 단일 출처 URL은 링크로도 남긴다.

PyMuPDF의 Circle 주석은 클릭·검토용 `/Rect`에 1pt 여유와 `/RD` 안쪽 여백을 남긴다. 실제 원 좌표와의 비교는 `annotation.rect + annotation.rect_delta`를 사용한다. 화면의 원은 주석 모양이 아니라 별도의 페이지 벡터이며, 글자 보호 클립 때문에 원의 외곽 일부가 잘릴 수 있다.

원문 텍스트 스트림, 글자색, 폰트, 페이지 회전·잘림, 원래 링크와 주석을 바꾸지 않는다. 텍스트를 다시 쓰거나 페이지를 이미지로 바꾸지 않는다. 새 이미지도 추가하지 않는다. 기존 주석의 모양 스트림과 메타데이터를 보존하는 회귀 검사도 포함했다.

## 작업량과 미리보기

페이지마다 최대 64개의 64pt 타일을 캐시한다. 하나의 원에서 정밀 분석하는 영역은 최대 160,000픽셀이며, 정밀 클립은 원당 1,024개 직사각형, 페이지당 약 40,000개 직사각형 또는 256개 원까지 계산한 뒤 보수적인 글자 상자 제외로 전환한다. 보수적인 제외 역시 원당 직사각형 수를 제한한다. 아주 작은 한도에서 같은 제외 계산이 재귀 반복되던 문제는 실패 검사를 먼저 추가해 수정했다.

`marked_document(..., page_numbers={쪽번호})`를 지원한다. 미리보기는 요청한 쪽만 칠하고 출처 주석도 그 쪽만 추가한다. 전체 PDF 내보내기는 모든 쪽을 같은 방식으로 처리한다. 두 쪽짜리 회귀 검사는 다른 쪽의 잉크 분석이 호출되지 않는지, 요청한 쪽의 결과가 전체 출력과 같은지 확인한다.

최종 코드의 100쪽·쪽당 원 1개·불투명 배경 합성 문서에서 한 쪽만 처리하는 데 0.048초, 전체 표시 문서를 만드는 데 4.823초가 걸렸다(Python 3.12, PyMuPDF 1.26.6, 이번 Linux 실행 환경의 단일 관측). 페이지 미리보기마다 전체 문서를 다시 칠하는 중복을 제거한 결과이며, 동시 사용자 부하 검사나 운영 지연 시간 보장은 아니다. 여러 PDF를 동시에 처리할 때의 메모리·CPU 한도는 별도 운영 검증이 필요하다.

## 자동 검증

```sh
python -m unittest tests.test_pdf_rendering -v
```

17개 검사 통과. 다음을 확인했다.

- 주석 표시 여부에 따라 원과 글자 모양이 달라지지 않음.
- 원래 검은 획 및 색상 글자의 내부 픽셀이 유지됨.
- 불투명 배경의 26pt 숫자·한글 fixture에서 1·1.5·1.65·2·3·4배 렌더링의 원래 비백색 픽셀이 안티앨리어싱 경계를 포함해 모두 유지됨. 기본 설정과 이동·색상·크기·불투명도 변경을 각각 확인함.
- 불투명 채움, 이미지, 불확실한 이미지 배경에서도 원이 보임.
- 회전 0°·90°·180°·270°, 잘린 페이지, 이동·크기 조절에서 원이 설정 범위에 그려지고 출처 주석의 안쪽 좌표가 실제 원 좌표와 일치함.
- 폰트·텍스트·글자 좌표·색상·기존 본문 스트림·링크·기존 Circle 주석·출처 정보가 유지됨.
- 반복 다운로드, 설정 변경, 표시 삭제가 결과에 반영됨.
- 타일 재사용, 작은 클립 한도, 요청한 쪽만 처리하는 미리보기가 동작함.

초기 0.5pt 보호 여유에서는 엄격한 브라우저 검사에서 글자 내부 검정은 유지됐지만 옅은 경계 픽셀 31개가 변했다. 실패 재현을 추가한 뒤 위의 1.5pt 보호와 정확한 배경 비교로 수정했다. 최종 숫자 브라우저 검사는 기본 표시, 수동 위치·설정 수정, 반복 다운로드, 화면 확대 단계에서 원래 비백색 픽셀을 엄격하게 비교한다.

투명 페이지의 정상적인 배경 원은 글자 아래에 있으므로 경계 픽셀이 새 파란 배경과 자연스럽게 합성될 수 있다. 또한 0.2배처럼 글자와 원이 같은 작은 픽셀을 공유하는 축소 화면에서는 비백색 경계 RGB의 완전 일치를 보장하지 않는다. 합성 숫자 fixture의 0.2배 실험에서는 기본·수정 설정에서 각각 경계 픽셀 24·29개가 달라졌고, 그 해상도에는 완전한 검정 내부 픽셀이 없었다. 글자·폰트·좌표의 구조적 보존과 보이는 원을 유지하며, 이를 모든 축소 화면의 픽셀 일치 통과로 기록하지 않는다.

## 실제 PDF 뷰어 확인

웹 앱의 PNG 화면을 Chrome에서 본 검사와 **Chrome 내장 PDF 뷰어로 PDF 파일 자체를 연 검사**를 구별했다. 아래 Chrome 결과는 로컬 HTTP 서버가 `application/pdf`로 제공한 파일을 250%로 연 것이다. Playwright의 프레임 및 CDP 대상에 `chrome-extension://mhjfbmdgcfjbbpaeojofohoefgiehjai/index.html`이 나타나는 것을 기록했고, PDF 도구 모음과 실제 문서 글자가 함께 보이는 스크린샷을 확인했다.

|환경|상태|관측|
|---|---|---|
|MuPDF 1.26.11 / PyMuPDF 1.26.6, Linux|실행|검은 획·색상 글자·배경·회전·주석 표시 여부의 회귀 검사 통과|
|Chromium 155.0.8059.79 내장 PDF 뷰어, Linux|실행|투명·불투명·색상 글자·이미지와 회전/잘림 fixture에서 원이 보이고 글자가 유지됨|
|macOS Preview|미실행 (UNRUN)|Linux 환경에서 실행할 수 없음. 통과로 기록하지 않음|
|Adobe Acrobat Reader|미실행 (UNRUN)|이 환경에 설치되어 있지 않음. 통과로 기록하지 않음|

Chrome 스크린샷의 원본과 새 출력을 같은 위치에서 비교한 결과:

|---|---:|---:|
|투명 배경, 검정 글자|4,700|0|
|불투명 흰 배경, 검정 글자|4,700|0|

Chrome은 기존 `Multiply` 출력도 정상 적용했다. 동일 문서에서 혼합 모드를 의도적으로 `Normal`로 바꾼 비교 파일은 검은 내부 픽셀 1,241개가 변하고 글자가 회색으로 보였다. 이는 **혼합 모드를 무시했을 때의 모의 재현**이며, Chrome이 실제로 혼합 모드를 무시했다거나 Preview/Reader에서 같은 문제가 재현되었다는 뜻은 아니다.

실제 뷰어 비교에는 한글 폰트를 내장한 합성 fixture를 사용했다. 기존 테스트의 내장되지 않은 CJK 기본 폰트 fixture는 Chrome에서 **원본부터** 글자가 보이지 않았다. 이 원본 폰트 호환성은 별도 제한으로 남기며, 표시 렌더러가 원문 폰트를 바꾸어 보정하지 않는다.

증거 파일은 Git에서 제외되는 `test-results/pdf-rendering/`에 있다.

- `viewer-evidence.json`: 뷰어 버전, PDF 응답 유형, 프레임·CDP 대상, 미실행 플랫폼 기록.
- `chromium-pixel-comparison.json`: 위 원본/출력 픽셀 비교.
- `*-chromium-pdf.png`: 실제 Chrome PDF 뷰어 스크린샷.
- `*-mupdf.png`: MuPDF 렌더링 비교 이미지.
- `mupdf-pixel-comparison.json`: 3배 MuPDF 비교. 투명·불투명·색상·이미지/회전 fixture의 단색 내부 변경은 각각 0/3,652, 0/3,652, 0/4,068, 0/3,651개.
- `*-source.pdf`, `*-new.pdf`, `old-multiply*.pdf`: 비교 입력과 출력.

Playwright·Pillow·fonttools, Chromium, Noto CJK TTC가 설치된 환경에서 실제 뷰어 증거를 재생성하는 명령 (`--chromium`, `--font-collection`으로 경로 지정 가능):

```sh
python3 tests/pdf_viewer_browser.py --output test-results/pdf-rendering
python3 tests/pdf_viewer_browser.py --output test-results/pdf-rendering --compare-only
```

뷰어 fixture를 만드는 과정에서만 한글 폰트를 내장한다. 양쪽 엔진의 원본에서 실제 글자 잉크가 존재하는지 먼저 확인하여 빈 원본이 비교를 통과하지 않도록 했다. 최종 렌더러로 다시 생성한 증거를 사용했으며, 출력 PDF의 원문 폰트를 수정한 것이 아니다.

대표 비교는 `opaque-new-chromium-pdf.png`와 `old-multiply-ignored-normal-chromium-pdf.png`다. 전자는 선명한 원래 검은 획을, 후자는 `Normal` 합성 재현의 회청색 획을 보여준다. Preview와 Reader의 최종 호환성 확인은 각각의 실제 환경에서 같은 PDF로 수행해야 한다.
