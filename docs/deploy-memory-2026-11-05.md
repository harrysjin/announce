# 512MiB 배포 검증 시도와 작은 PDF 메모리 관측

2026-11-05 UTC에 작은 PDF의 실제 분석·출력·삭제를 완료했고 서버 프로세스의 최대 RSS는 **416.309MiB**였습니다.
**512MiB 제한 안에서의 실행 성공은 아직 확인하지 못했습니다.** 이 클라우드의 rootless Docker가 메모리 제한을 강제하지 못하므로 실제 Render 환경에서 추가 확인해야 합니다.

## 제한이 적용되는지 먼저 확인

컨테이너에 `--memory 512m --memory-swap 512m`를 전달했고 Docker `HostConfig.Memory`와 `MemorySwap`에 각각 `536870912`가 반영됐습니다.
그러나 실제 실행 환경은 다음과 같았습니다.

| 관측 항목 | 결과 |
| --- | --- |
| Docker CgroupDriver | `none` |
| Docker MemoryLimit / SwapLimit 지원 | `false` / `false` |
| 컨테이너 `/sys/fs/cgroup/memory.max` | `34359738368` · 32GiB |
| 컨테이너 `/sys/fs/cgroup/memory.swap.max` | `max` |
| Docker 경고 | `Running in rootless-mode without cgroups. Systemd is required to enable cgroups in rootless-mode.` |

이 때문에 첫 제한 검사는 사전 요청 전에 중단했습니다. 메모리 제한 옵션이 설정됐다는 사실을 제한 적용의 증거로 사용하지 않았습니다.
daemon·cgroup·마운트 권한을 변경하지 않았습니다.
첫 검사용 컨테이너는 정리를 위한 `docker stop` 후 종료 코드 137, `OOMKilled=false`였으므로 이를 512MiB에서 발생한 OOM으로 해석하지 않습니다.

## 실제 작은 문서의 처리 결과

최신 Docker 이미지에서 Uvicorn worker 1개, `ANALYSIS_CONCURRENCY=1`로 실행했습니다.
Kiwi 0.24.1과 모델 0.24.0을 사용했고 `load_typo_dict=False`, `load_multi_dict=False`를 적용했습니다.
기본 어휘·형태소 모델은 유지한 설정입니다. 별도 프로세스에서 Kiwi를 띄우지 않고 실제 API 서버에서 준비·분석했습니다.
API 키는 런타임 환경변수로만 전달했고 기존 프록시·CA·TLS 검증을 유지했습니다.

- 준비: `천천히` 1어절 PDF의 공식 사전 분석 완료, 표시 1개, 분석 4.062초. 작업 삭제 후 접근 404 확인.
- 본 검사: `천천히 낭독 눈 말 사람`이 있는 1쪽·5어절·1,141바이트의 텍스트 PDF. 공식 사전 분석 완료, 자동 표시 3개, 분석 15.719초.
- 미리보기: 1.5배 PNG 렌더링 성공, 893×1263픽셀.
- 출력: PDF·Markdown·CSV 다운로드 성공. PDF 원문 보존 서명, 내장 검증 기록 1개, 표시 개수 일치 확인.
- 삭제: 본 작업 삭제 후 접근 404 확인. 종료 전 Docker 상태는 `healthy`.

## 서버 프로세스 RSS 관측

각 단계에서 컨테이너 PID 1의 `/proc/1/status`에 있는 `VmRSS`와 커널 최고치 `VmHWM`을 읽었습니다.
아래 시점은 컨테이너 시작부터의 경과 시간이며 분석 시간에는 업로드와 관측 명령 시간이 포함되지 않습니다.

| 단계 | 경과 시간 | RSS · MiB | VmHWM · MiB |
| --- | ---: | ---: | ---: |
| 서버 준비 | 2.311초 | 81.910 | 81.910 |
| Kiwi 준비와 준비 작업 삭제 후 | 6.465초 | 401.441 | 401.441 |
| 5어절 분석 완료 | 23.286초 | 404.559 | 404.559 |
| 미리보기 렌더 후 | 23.390초 | 416.109 | 416.109 |
| PDF·Markdown·CSV 출력 후 | 23.476초 | 416.309 | 416.309 |
| 두 작업 모두 삭제 후 | 23.535초 | 416.309 | 416.309 |

최대 `VmHWM`의 원시 값은 `426300 kB`이며 1024로 나누어 MiB로 표시했습니다.
이 값은 서버 프로세스의 RSS입니다. 컨테이너 전체 메모리 예산이나 파일 캐시·다른 프로세스를 포함한 cgroup 최고치로 바꿔 해석하지 않습니다.

Docker Engine의 `memory_stats.limit`도 `34359738368`를 반환했고, 관측된 `usage`는 약 13.5~13.9GiB였습니다.
Docker CLI `stats`의 한 번 관측값은 `3.896GiB / 32GiB`였습니다.
이 값들은 해당 작은 서버 프로세스의 사용량과 일치하지 않는 공유 cgroup 관측값이므로 문서 처리의 메모리 최고치로 사용하지 않았습니다.
같은 이유로 이 환경의 `memory.peak`나 `memory.events`를 해당 컨테이너만의 512MiB 검증 근거로 사용하지 않았습니다.

본 검사의 종료 전후 `OOMKilled=false`였고, 모든 작업을 마친 뒤 의도한 `docker stop`의 종료 코드는 **0**이었습니다.

## 이 결과가 확인하지 않은 범위

이 검사는 1쪽의 작은 텍스트 PDF를 순서대로 처리한 결과입니다.
20MB·100쪽 한도 전체, 복잡한 PDF, 여러 사용자의 업로드·미리보기·출력 동시 실행, 반복·장시간 안정성을 검증하지 않았습니다.
선택 사전 두 개를 끈 설정만 측정했으며 이 메모리 검사가 설정 간 분석 품질의 동등성을 입증하지는 않습니다.

Render의 실제 512MiB 제한에서 시작·첫 분석·미리보기·출력의 메모리 지표와 OOM/재시작 로그를 확인해야 무료 인스턴스의 처리 범위를 판단할 수 있습니다.
현재 관측값만으로 512MiB 운영 적합성이나 전체 업로드 한도의 처리를 보장하지 않습니다.
